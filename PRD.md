ТЗ: AI-агент продуктивности на базе Hermes Agent + Telegram + Notion + TickTick

1. Название проекта

Personal Productivity AI Agent — персональный AI-ассистент для управления задачами, проектами и ежедневным планированием через Telegram.

⸻

2. Цель проекта

Создать персонального AI-агента, который ежедневно анализирует задачи пользователя из Notion и TickTick, формирует дейли-брифинг, дает рекомендации по приоритетам, помогает планировать день/неделю и позволяет общаться с ним через Telegram.

Система должна не просто показывать список задач, а помогать принимать решения:

* что делать сегодня в первую очередь;
* какие задачи горят по дедлайну;
* какие задачи можно перенести;
* где есть перегрузка;
* какие проекты стоят без движения;
* какие следующие действия нужны по каждому проекту;
* как лучше распределить задачи по времени, энергии и приоритету.

⸻

3. Общая концепция

Пользователь ведет:

* Notion — проекты, рабочие задачи, проектные базы, TODO по проектам;
* TickTick — личные задачи, бытовые дела, привычки, планер жизни;
* Telegram — основной интерфейс общения с AI-ассистентом.

Hermes Agent используется как агентная основа: принимает сообщения из Telegram, вызывает кастомные skills/tools, получает данные из Notion и TickTick, анализирует их через LLM и возвращает пользователю структурированный ответ.

⸻

4. Основные сценарии использования

4.1. Утренний дейли-брифинг

Каждое утро в заданное время агент автоматически присылает в Telegram краткий отчет:

* главный фокус дня;
* 3–5 ключевых задач;
* срочные задачи с дедлайнами;
* задачи из личного планера TickTick;
* задачи из проектных баз Notion;
* предупреждения о перегрузке;
* рекомендации по порядку выполнения;
* что можно перенести;
* короткий план дня по блокам.

Пример команды:

/briefing

Пример ответа:

Доброе утро.
Главный фокус дня:
— Завершить задачу по проекту X, потому что дедлайн сегодня.
Критичные задачи:
1. ...
2. ...
3. ...
Личные задачи:
— ...
Рекомендация:
Сначала закрыть задачу с дедлайном, затем выполнить 2 короткие задачи до 30 минут.

⸻

4.2. Вечерний review

Каждый вечер агент присылает сообщение:

* что было запланировано;
* что выполнено;
* что не выполнено;
* что перенести;
* какие задачи зависли;
* краткая рекомендация на завтра.

Пример команды:

/review

Агент может спросить:

Что из сегодняшнего списка выполнено?
Ответь номерами задач или коротким текстом.

⸻

4.3. Планирование дня по запросу

Пользователь пишет:

Что мне делать сегодня?

Агент должен:

1. Получить актуальные задачи из Notion и TickTick.
2. Отфильтровать задачи на сегодня и ближайшие дедлайны.
3. Оценить приоритеты.
4. Предложить реалистичный план.
5. Выделить 1 главный фокус.

⸻

4.4. Планирование недели

Команда:

/week

Агент должен дать:

* обзор задач на неделю;
* ближайшие дедлайны;
* проекты с высоким приоритетом;
* дни с перегрузкой;
* рекомендации по перераспределению задач;
* список задач без дедлайна, которые требуют уточнения.

⸻

4.5. Работа с проектами из Notion

Команда:

/project CrossMeet

Агент должен показать:

* статус проекта;
* активные задачи;
* ближайшие дедлайны;
* зависшие задачи;
* следующие рекомендуемые действия;
* риски по проекту.

⸻

4.6. Работа с личными задачами из TickTick

Команда:

/life

Агент должен показать:

* личные задачи на сегодня;
* бытовые дела;
* повторяющиеся задачи;
* просроченные задачи;
* задачи без времени;
* рекомендации по распределению.

⸻

4.7. Добавление новых задач

Пользователь пишет естественным языком:

Добавь задачу: завтра в 12:00 позвонить врачу

Агент должен:

1. Распознать задачу, дату и время.
2. Уточнить, куда добавить: TickTick или Notion, если это не очевидно.
3. Создать задачу.
4. Подтвердить создание.

Для MVP добавление задач можно ограничить TickTick.

⸻

4.8. Изменение статуса задач

Пользователь пишет:

Отметь задачу «Подготовить отчет» как выполненную

Агент должен:

1. Найти задачу.
2. Если найдено несколько похожих — уточнить выбор.
3. Обновить статус.
4. Подтвердить действие.

Для MVP изменение статусов можно сначала отключить и оставить только чтение.

6. Нефункциональные требования

6.1. Надежность

* Система должна работать ежедневно без ручного запуска.
* При ошибке API Notion/TickTick агент должен сообщать, какой источник недоступен.
* Если один источник недоступен, брифинг должен строиться по оставшимся данным.
* Ошибки должны логироваться.

⸻

6.2. Безопасность

* API-ключи и токены должны храниться только в переменных окружения или защищенном vault.
* Нельзя хранить токены в открытом репозитории.
* Notion-интеграции дать доступ только к нужным базам, а не ко всему workspace.
* Действия изменения задач должны быть подтверждаемыми, если есть риск ошибки.
* Удаление задач через агента в первой версии запретить.
* Telegram-бот должен отвечать только авторизованному пользователю.

⸻

6.3. Приватность

* Данные задач не должны отправляться в лишние внешние сервисы.
* Логи не должны содержать полные API-токены.
* Желательно не логировать полные тексты личных задач, если это не нужно для отладки.

⸻

6.4. Масштабируемость

На первом этапе система рассчитана на одного пользователя.

Архитектура должна позволять в будущем добавить:

* несколько пользователей;
* несколько Telegram-чатов;
* отдельные профили: работа, учеба, жизнь;
* новые источники: Google Calendar, Gmail, Apple Calendar, GitHub, Bitrix24.

8. Логика приоритизации

Базовая формула приоритета:

Priority Score = Deadline urgency + User priority + Project importance + Task age + Blocking factor - Low energy penalty

Пример правил:

* дедлайн сегодня → высокий приоритет;
* задача просрочена → высокий приоритет;
* задача в проекте с активным дедлайном → повышенный приоритет;
* задача без следующего действия → вынести в отдельный блок;
* слишком много задач на день → предложить перенос;
* задача со статусом Waiting → не ставить в главный фокус;
* личные задачи с конкретным временем → учитывать как фиксированные блоки.

9. Режимы работы агента

9.1. Read-only режим

Первая версия системы.

Агент может:

* читать задачи;
* анализировать;
* давать рекомендации;
* формировать брифинги.

Агент не может:

* изменять задачи;
* удалять задачи;
* переносить дедлайны;
* закрывать задачи.

9.2. Controlled-write режим

Вторая версия.

Агент может изменять задачи только после подтверждения:

Я нашел задачу «...». Перенести ее на завтра?
Ответь: да / нет.

9.3. Semi-autonomous режим

Третья версия.

Агент может сам выполнять безопасные действия:

* создать новую личную задачу;
* отметить задачу как выполненную после явной команды;
* перенести низкоприоритетную задачу после подтверждения.

Удаление задач запрещено или требует отдельного подтверждения.

⸻

10. Первая рабочая версия

Первая версия должна быть не урезанным read-only MVP, а полноценной рабочей системой с возможностью чтения, анализа и управления задачами.

10.1. Что входит в первую версию

1. Hermes Agent установлен на VPS-сервере.
2. Подключен Telegram-бот.
3. Реализована авторизация по Telegram ID.
4. Реализован OpenRouter API как основная LLM.
5. Реализован Notion Connector для нескольких баз данных.
6. Реализован TickTick Connector.
7. Реализовано чтение задач из Notion и TickTick.
8. Реализовано создание задач в TickTick и Notion.
9. Реализовано закрытие задач.
10. Реализован перенос задач.
11. Реализовано изменение дедлайнов.
12. Реализовано изменение статусов задач.
13. Реализован утренний брифинг в 07:30 по МСК.
14. Реализован вечерний review в 21:00 по МСК.
15. Реализована команда /today.
16. Реализована команда /briefing.
17. Реализована команда /week.
18. Реализована команда /project.
19. Реализована команда /life.
20. Реализованы команды /add, /done, /reschedule, /focus, /stuck.
21. Реализовано логирование ошибок.
22. Все ключи вынесены в .env.
23. Система автоматически запускается после перезагрузки VPS.

10.2. Что не входит в первую версию

* Мультипользовательский режим.
* Голосовые сообщения.
* Отдельный веб-дашборд.
* Глубокая аналитика продуктивности за месяц/квартал.
* Подключение Google Calendar / Apple Calendar.
* Подключение Gmail.
* Подключение Bitrix24.
* Полностью автономное удаление задач без подтверждения.

14. Prompt-логика для LLM

Системный стиль агента:

* говорить кратко и по делу;
* не просто перечислять задачи, а давать решение;
* не перегружать пользователя;
* выделять главный фокус;
* объяснять рекомендации коротко;
* не придумывать задач, которых нет в источниках;
* явно отделять факты от рекомендаций;
* если данных не хватает — писать, что именно не хватает.

Пример инструкции для генерации брифинга:

Ты персональный ассистент продуктивности. На основе задач из Notion и TickTick сформируй краткий дейли-брифинг.
Правила:
1. Не выдумывай задачи.
2. Сначала покажи главный фокус дня.
3. Отдельно покажи срочные задачи.
4. Отдельно покажи личные задачи.
5. Если задач слишком много, предложи что перенести.
6. Дай конкретный порядок выполнения.
7. Ответ должен быть на русском языке.
8. Не больше 2500 символов.

По умолчанию используется часовой пояс Europe/Moscow / МСК.

Автоматизация	Время	Частота
Утренний брифинг	07:30 МСК	Каждый день
Вечерний review	21:00 МСК	Каждый день
Недельный обзор	10:00 МСК, воскресенье	1 раз в неделю
Проверка просроченных задач	12:00 МСК	Каждый день

Время должно быть настраиваемым через переменные окружения или настройки агента.

16. Обработка ошибок

Если недоступен Notion:

Не удалось получить задачи из Notion. Брифинг составлен только по TickTick.

Если недоступен TickTick:

Не удалось получить личные задачи из TickTick. Брифинг составлен только по Notion.

Если оба источника недоступны:

Не удалось получить задачи из Notion и TickTick. Проверь API-ключи или подключение.

⸻

17. Критерии приемки MVP

MVP считается готовым, если:

1. Пользователь может написать боту в Telegram и получить ответ.
2. Бот отвечает только авторизованному Telegram ID.
3. Команда /today возвращает задачи из Notion и TickTick.
4. Команда /briefing формирует структурированный брифинг.
5. Команда /week формирует обзор недели.
6. Команда /project <название> показывает статус проекта из Notion.
7. Утренний брифинг приходит автоматически по расписанию.
8. Вечерний review приходит автоматически по расписанию.
9. При сбое одного источника система не падает полностью.
10. Все токены хранятся в переменных окружения.
11. В логах нет открытых API-ключей.
12. Система перезапускается после reboot сервера.

19. Риски и ограничения

1. У TickTick API может быть меньше возможностей, чем нужно для сложного управления задачами.
2. Структура Notion-баз должна быть достаточно формализованной, иначе анализ будет менее точным.
3. Агент может ошибаться в приоритизации, поэтому первые версии должны быть рекомендательными, а не автономными.
4. Изменение задач через AI нужно включать только после тестирования режима чтения.
5. Если брифинг будет слишком длинным, пользователь перестанет им пользоваться — нужен краткий формат.
6. Cron-задачи должны быть самодостаточными: в них нужно явно указывать, что получить, как анализировать и куда отправить результат.

22. Особые требования из-за нескольких баз Notion

Так как задачи в Notion находятся в нескольких базах, нужно реализовать слой конфигурации Notion-баз.

Каждая база должна быть описана в конфиге:

{
  "databases": [
    {
      "name": "Work Tasks",
      "database_id": "...",
      "type": "tasks",
      "area": "work",
      "fields_map": {
        "title": "Name",
        "status": "Status",
        "deadline": "Deadline",
        "priority": "Priority",
        "project": "Project"
      }
    },
    {
      "name": "Study Tasks",
      "database_id": "...",
      "type": "tasks",
      "area": "study",
      "fields_map": {
        "title": "Name",
        "status": "Status",
        "deadline": "Date",
        "priority": "Priority",
        "project": "Course"
      }
    }
  ]
}

Требования:

1. Агент должен уметь читать задачи из всех подключенных баз.
2. Агент должен приводить задачи из разных баз к единому формату.
3. Для каждой базы нужно указать соответствие полей, потому что названия полей в разных Notion-базах могут отличаться.
4. При создании задачи агент должен понимать, в какую базу ее добавить.
5. Если база не очевидна, агент должен уточнить у пользователя.
6. Команда /project должна искать проект/задачи по всем подключенным Notion-базам.
7. В брифинге нужно указывать источник задачи: Notion-база или TickTick.

⸻

23. Требования к write-функциям первой версии

Так как система должна сразу уметь управлять задачами, необходимо реализовать следующие действия.

23.1. Создание задачи

Команда:

/add Завтра в 12:00 позвонить врачу

Агент должен:

1. Распознать название задачи.
2. Распознать дату и время.
3. Определить источник: TickTick или Notion.
4. Если источник не очевиден — уточнить.
5. Создать задачу.
6. Подтвердить создание.

23.2. Закрытие задачи

Команда:

/done Подготовить отчет

Агент должен:

1. Найти задачу по всем источникам.
2. Если найдено одно точное совпадение — предложить подтверждение.
3. Если найдено несколько похожих задач — показать список и попросить выбрать номер.
4. После подтверждения отметить задачу как выполненную.

23.3. Перенос задачи

Команда:

/reschedule Подготовить отчет на завтра

Агент должен:

1. Найти задачу.
2. Распознать новую дату.
3. Показать пользователю, что именно будет изменено.
4. После подтверждения обновить дату.

23.4. Изменение статуса

Команда:

Поставь задачу «Дизайн модального окна» в In Progress

Агент должен:

1. Найти задачу.
2. Проверить допустимые статусы для базы-источника.
3. Изменить статус.
4. Подтвердить действие.

23.5. Запрет на опасные действия

В первой версии запрещено выполнять без подтверждения:

* удаление задач;
* массовое изменение задач;
* перенос всех просроченных задач;
* изменение задач, если совпадение найдено неточно;
* изменение задач в неизвестной Notion-базе;
* любые действия, если не удалось определить источник задачи.
