# Wiki проекта

Этот документ фиксирует рабочие правила Personal Productivity AI Agent: что система делает, какие границы у MVP и какие решения нельзя нарушать без явного изменения PRD.

## Общая идея

Агент помогает одному пользователю управлять задачами через Telegram. Notion используется для проектных и рабочих задач, TickTick — для личных задач и бытового планирования, OpenAI — для кратких рекомендаций и разговорного слоя. Если OpenAI недоступен, сервис должен продолжать отвечать через локальный анализатор.

Главная ценность проекта — не просто показать список задач, а помочь выбрать следующий шаг: главный фокус, срочные дедлайны, зависшие задачи, перегрузку и переносимые элементы.

## Что можно делать

- Читать задачи из Notion и TickTick.
- Показывать план на день, неделю, вечерний review, личные задачи и статус проекта.
- Создавать задачи в TickTick или Notion, если источник явно выбран и настроен.
- Закрывать, переносить и менять статус задач после подтверждения пользователя.
- Искать похожие задачи через fuzzy matching и просить выбрать номер при неоднозначности.
- Записывать локальные метрики эффективности: завершение работы, отход ко сну, фактический сон, выполнение главного фокуса.
- Отвечать обычным текстом в Telegram с учетом последних сообщений и текущего списка задач.
- Продолжать работу при частичном отказе источников: если Notion недоступен, использовать TickTick, и наоборот.

## Что нельзя делать

- Нельзя выполнять write-операции без подтверждения `да` от авторизованного пользователя.
- Нельзя менять несколько похожих задач, если пользователь не выбрал конкретную.
- Нельзя утверждать, что задача создана, закрыта или перенесена, пока API источника не вернул успешный результат.
- Нельзя показывать пользователю служебные поля: JSON, payload, metadata, score, generated_at, timezone, модель, технические ошибки API.
- Нельзя хранить реальные токены в репозитории, README, wiki или примерах.
- Нельзя расширять доступ за пределы одного пользователя без пересмотра модели авторизации.
- Нельзя молча игнорировать недоступный источник: в ответе нужно коротко указать, что Notion или TickTick недоступен.
- Нельзя выдумывать задачи, дедлайны, проекты или статусы, которых нет в источниках.

## Источники данных

### Notion

Notion может быть настроен через `NOTION_DATABASES_JSON` или legacy-переменные `NOTION_TASKS_DATABASE_ID` и `NOTION_PROJECTS_DATABASE_ID`. Для нескольких баз предпочтителен JSON-формат, потому что он позволяет задать имя базы, тип, область и карту полей.

Рекомендуемые поля задач:

- `Name` — название задачи.
- `Status` — статус.
- `Deadline` или аналогичное date-поле.
- `Priority` — приоритет.
- `Project` — проект или курс.
- `Area` — область жизни/работы.
- `Energy` — требуемая энергия.
- `Estimated time` — оценка времени.
- `Notes` — заметки.

### TickTick

TickTick используется для личных задач и может хранить OAuth-токены в `.state/agent-state.json`. Для авторизации есть CLI-команды:

```bash
agent-productivity-cli ticktick-authorize
agent-productivity-cli ticktick-auth-url
agent-productivity-cli ticktick-exchange-code <code>
```

### OpenAI

OpenAI используется для генерации русскоязычных ответов по компактному payload задач. При отсутствии `OPENAI_API_KEY` или ошибке API работает deterministic fallback из `ProductivityAnalyzer`.

## Telegram-поведение

Бот принимает только сообщения от `TELEGRAM_ALLOWED_USER_ID`. Неавторизованные пользователи получают `Нет доступа.`.

Плановые сообщения:

- утренний брифинг каждый день в `MORNING_BRIEFING_TIME`;
- вечерний review каждый день в `EVENING_REVIEW_TIME`;
- недельный обзор по воскресеньям в `WEEKLY_REVIEW_TIME`;
- проверка зависших/просроченных задач в `OVERDUE_CHECK_TIME`.

Ответы Telegram обрезаются до 4096 символов, поэтому генерация должна оставаться компактной.

## Состояние приложения

Локальное состояние хранится в `APP_STATE_PATH`, по умолчанию `.state/agent-state.json`.

В нем находятся:

- pending actions для подтверждения write-операций;
- OAuth-токены TickTick, если они получены через CLI;
- записи эффективности.

Файл `.state/` не должен попадать в git.

## Подтверждения действий

Типичный write-flow:

1. Пользователь отправляет `/done отчет` или похожую команду.
2. Сервис собирает активные задачи из источников.
3. `TaskRepository.find_candidates` ищет совпадения.
4. Если совпадение сильное, создается pending action.
5. Если совпадений несколько, пользователь выбирает номер.
6. Пользователь отвечает `да`.
7. Только после этого вызывается API Notion или TickTick.

Отмена: `нет`, `no`, `n`, `отмена`, `cancel`. Подтверждение: `да`, `yes`, `y`, `ок`, `подтверждаю`.

## Разработка

Перед изменением поведения стоит читать `PRD.md`, `README.md` и этот файл. Для safety-flow write-операций дополнительно смотреть тесты в `tests/test_safety_flow.py`.

Базовые команды:

```bash
pytest
ruff check .
agent-productivity-cli doctor
```

При изменении коннекторов нужно добавлять или обновлять тесты на недоступный источник, нормализацию задачи и write-операции. При изменении Telegram-команд нужно проверять и slash-команду, и естественную фразу, если такая поддерживается.

## Известные ограничения

- Проект рассчитан на одного пользователя.
- Нет отдельной базы данных; состояние хранится в JSON-файле.
- LLM не является источником истины и не должен выполнять изменения напрямую.
- Качество Notion-интеграции зависит от корректной карты полей.
- TickTick OAuth зависит от внешнего redirect-flow и может требовать ручной настройки приложения.
- Длинные ответы Telegram обрезаются.
